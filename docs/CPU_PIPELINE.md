# Конвейер QR / PDF — 29.10.2026

## Как сравнить на своём ПК

Перезапустите `Start-uCode.cmd` тестовой копии `016_uCode_PDF_test`. Откройте вкладку **Конвейер** или **Тесты → Конвейер: QR и PDF на разных CPU**.

1. **Кодов в PDF**: добавьте своё число, затем оставьте нужные количества в меню. Ограничения 10 000 здесь нет; действуют проверки ресурсов.
2. **QR + PDF**: отметьте сравниваемые распределения. На ПК 14 ядер / 28 SMT доступны 12+2, 24+4, 14+0, 28+0. Последние два выполняют кодирование и подготовку страницы в одном процессе. Это параметры распределения, а не скрытые сценарии тестов.
3. Для другого соотношения выберите **Ядра / Потоки SMT**, число QR и PDF, нажмите **Добавить**. PDF=0 означает полный цикл; QR должно быть не меньше одного. Сумма не может превышать доступные CPU выбранного типа. Недоступный сохранённый набор получает SKIPPED с причиной.
4. **Распределение**: «Равные части», «Общая очередь» или оба. В первом режиме диапазоны закреплены за каждым процессом обоих этапов. Во втором свободный процесс берёт следующую порцию.
5. **Кодов за шаг**: размер передаваемой порции, 1–1000. В обоих способах сообщения ограничены этим размером. Можно сравнить несколько размеров или добавить свой. Это не число ядер и не количество полных повторов.
6. **Повторов**: 1–10. Один повтор даёт предварительный результат; три и более помогают увидеть разброс. Прогрев выключен и в результаты не добавляется скрытых прогонов.
7. **ОЗУ**: безопасный бюджет для полезных пакетов с резервом ОС; принудительного заполнения памяти нет. **Замеры CPU**: ВКЛ, ВЫКЛ, либо отдельные варианты обоих режимов. Защита RAM и отмена действуют всегда.
8. Общий переключатель **С проверкой / Без проверки / Частично** задаёт QA серии. Без проверки: UNVERIFIED, QA=0. Полная проверка включает независимое чтение векторов всех страниц и растровые образцы. QA FAIL исключает вариант из сравнения.
9. Проверьте строку «Вариантов / повторов / результатов» и нажмите **ЗАПУСТИТЬ КОНВЕЙЕР**. Каждый повтор создаёт отдельный настоящий PDF. После завершения **Отчёт в браузере** открывает HTML через браузер по умолчанию, рядом доступны файлы и CSV.

Примеры точного количества результатов: 2000 кодов, два распределения, один способ, один размер порции, один режим замеров и один повтор = 2 результата. 10 000 кодов, три распределения, один способ, десять повторов = 30 результатов. Для 12+2 и 24+4, обоих способов, одной порции, трёх повторов = 12 результатов. Сравнение ВКЛ/ВЫКЛ удваивает их число.

## Архитектура и границы

`pipeline_plan.py` проверяет настройки и топологию CPU, строит точную матрицу и диапазоны. Физический режим выбирает по одному логическому CPU каждого ядра. SMT-соседи сортируются по реальному core ID: 24+4 на полном 14/28 процессоре разделяют целые ядра как 12+2. Если пользователь выбирает нечётную границу SMT и этапы делят ядро, отчёт явно это указывает. Доступность и ограничения affinity учитываются по текущей ОС; Windows multi-group пока SKIPPED. Привязка ограничивает uCode, а не запрещает другим программам использовать эти CPU.

`pipeline.py` запускает изолированные spawn-процессы. При PDF>0: QR-процессы → ограниченная очередь матриц → PDF-процессы (геометрия и Flate) → один окончательный сборщик. При PDF=0 каждый процесс готовит QR и сжатый поток страницы. Сборщик работает на наборе PDF (либо общем пуле при PDF=0), **не получает дополнительного ядра** и не называется параллельным писателем одного файла.

Все процессы подтверждают собственную маску и проходят барьер готовности перед первой задачей. При равных частях N значений делятся через divmod: 100 000 / 28 = 12 диапазонов по 3572 и 16 по 3571. Каждый диапазон передаётся небольшими порциями, а не одним огромным ответом. В очереди задача назначается освободившемуся процессу. Маска GUI не меняется; изменение маски родителя конвейера допустимо только внутри дочернего lab worker.

Одна порция в работе на процесс; накопление ожидающих матриц ограничено числом QR CPU и размером порции. Предварительная оценка памяти: базовые 256 МиБ + 128 МиБ на процесс + не более min(N, 2×число процессов×порция) значений по консервативным 40 000 байт. Это оценка, а не измеренный пик; job/RSS guard обеспечивает отдельную защиту. RAW матрицы передаются Python IPC, zero-copy/shared-memory пока нет.

`stream_pdf.write_pdf(prepared=...)` принимает страницы в порядке готовности; SQLite-индекс восстанавливает исходный порядок в `/Kids`. Никакой завершающий PDF merger не нужен. Финальный PDF остаётся векторным DeviceCMYK, размеры/белое поле и QA-допуски сохранены. Геометрия/Resources наследуются от одного Pages-узла, координаты сетки вычисляются один раз на PDF-процесс, прямоугольники объединяются в компактном профиле. Обычный writer и его прежний формат совместимы; старые индексы читаются без нового поля. Новый reader независимо перечитывает реальные xref, порядок, геометрию и content, не принимает индекс за доказательство QA.

`pipeline_lab.py` использует прежние `_run_trial`, frozen runtime, контроль версии, RAM/job/cancel и CPUTrace. Настройки сохраняются в `.local-state/pipeline-settings.json`. Все повторы и ошибочные/прерванные результаты остаются локально; старые файлы не перезаписываются. Отдельная новая серия не смешивается с исторической научной методикой или обычной генерацией. Нынешний «Подбор ПК» не запускает скрыто эту новую ось.

## Измерения

В отчёте: каждая попытка, медиана/min/max полного времени, скорость кодов/с, время создания PDF и QA, байты PDF, наблюдаемый пик RSS и подтверждённые CPU-процессы. JSON дополнительно содержит, сколько страниц обработал каждый процесс, его этап, маску и сумму времени работы.

Основной рейтинг — фактическое `launcher_wall`: запуск Python, импорты, TXT, работа процессов, PDF, выбранная проверка, завершение. `production` / `pipeline_wall` — участок непосредственно создания PDF. `qr_service_sum` и `pdf_service_sum` — **суммы времени задач параллельных процессов**, они перекрываются и не складываются в общее время. `assembler_active` — активные участки записи каждой страницы с индексом/прогрессом, без ожидания процессов и завершающей записи xref; это не всё время записи.

CPU min/среднее/max и сырые интервалы доступны по ссылке в отчёте. Проценты относятся к собственным процессам с подтверждённой привязкой; это не общая загрузка Windows. Короткие процессы/пики могут быть пропущены. ВКЛ/ВЫКЛ сравниваются только при одинаковых allocation/schedule/batch, размер/режим QA общий для серии. Разные режимы замеров получают отдельные рейтинги. Быстрейшим признаётся только вариант с полным набором корректных повторов; незавершённая серия имеет видимое предупреждение.

Победитель 12+2 против 24+4 заранее неизвестен. Больше процессов может увеличить IPC, конкуренцию SMT и запуск. Больше ОЗУ не создаёт вычислительных блоков. Полная загрузка CPU сама по себе не равна меньшему времени. Последовательная сборка/xref, IPC, disk/index и независимая QA остаются возможными ограничениями. Большие сравнения 200/1000/10000/100000 запускает пользователь.

Источники контрактов runtime: [Python multiprocessing / spawn / Pipes](https://docs.python.org/3.12/library/multiprocessing.html), [perf_counter](https://docs.python.org/3.12/library/time.html#time.perf_counter).

## Проверка и обновление

Автоматические PDF не превышают 7 страниц. Проверяются векторные и растровые страницы, оба распределения работы, полный цикл, границы памяти, отмена, отсутствие QA и подробной CPU-телеметрии в режиме ВЫКЛ, независимость GUI affinity, точное число результатов. Математика 100 000 / 28 проверяется без генерации такого тиража. Геометрия Tk при 100/125/150% проверяется программно; видимую приёмку выполняет пользователь.

Сохранённые реальные отчёты: `output/pipeline-proof/`, очищенная сводка: `results/cpu-pipeline/verification.json`. Точные свежие команды/итоги и ограничения — в `WORK_LOG.md`.

Ветка `codex/cpu-pipeline-tests` основана на `codex/generation-core-controls` (PR16). Main не меняется. Для другой копии обновление допустимо в чистую ветку/отдельную папку с сохранением собственных правок, TXT, output и .local-state; не применять reset/clean поверх изменений. Уже открытое окно использует старый код до перезапуска. Обычную генерацию не переключаем на экспериментальный конвейер до большого сравнения.
