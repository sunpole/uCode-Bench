# uCode History Capture — пилот 2026-10-31

Цель: автоматически сохранять реальные снимки интерфейсов **точно определённых
исторических версий** приложения, а не имитации, рендеры ИИ или актуальный
main, ошибочно названный старым релизом.

## Этап 1 — реализован в отдельной PR-ветке, требует CI-проверки

- .github/workflows/history-capture.yml запускается для PR, вручную
  (workflow_dispatch, параметр tag) и при новых опубликованных Releases.
- Исходники программы извлекаются из **указанного Git-тега** в отдельную папку.
  Скрипт scripts/history_capture.py проверяет установленный пакет и версию,
  запускает локальный HTTP GUI в одноразовой папке и ждёт window.ucodeReady.
- Chromium через Playwright снимает вкладки с фиксированным экраном
  1440×900, русским языком, тёмной темой и масштабирующим коэффициентом 1.
  API доступен лишь на 127.0.0.1, посторонние запросы блокируются.
- Для каждого снимка записываются размер, SHA-256 и название вкладки.
  Общий manifest.json включает тег, точный commit, версию, способ съёмки,
  дату, успешность и число файлов. Токен локального сервера не публикуется.
- PNG и JSON загружаются **только во временный Actions artifact (30 дней)**.
  Архив не публикуется в main, Releases или sunpole/uCode.
- Не запускаются PDF-генерация, тесты производительности или очистка
  пользовательских папок.

Пилотный тег: v0.3.4. Для версий 0.3.0 и 0.2.0 может потребоваться
отдельный адаптер. Если старая версия не запускается, CI обязан завершиться
ошибкой и оставить диагностический manifest вместо выдуманной картинки.

## Как проверить

1. Откройте PR и дождитесь выполнения CI «uCode History Capture (real UI)».
2. Убедитесь, что job capture-browser завершилась SUCCESS.
3. В Actions → run → Artifacts скачайте ucode-history-capture-...
4. Проверьте PNG и JSON: status=PASS, версия 0.3.4, количество файлов,
   названия вкладок и соответствие контрольных сумм.
5. Проверьте содержимое реальных снимков глазами, включая отсутствие
   персональных данных и правильность интерфейса. Успешный CI сам по себе
   не означает визуальной пользовательской приёмки.

## Ограничения и второй этап

Этот пилот захватывает **браузерный HTML-интерфейс** реальной версии uCode,
а не нативные рамки WebView2 или Tkinter. Для них нужны отдельные стратегии
Windows GUI и активная графическая сессия.

GitHub Actions Artifacts временные. Для постоянной публичной истории нужен
второй, отдельный процесс публикации **после визуальной проверки пилота**:
предпочтительно в sunpole/uCode/history/, с ограниченной кросс-репозиторной
авторизацией (GitHub App или fine-grained token), проверкой разрешённых
файлов, идемпотентностью и политикой неизменяемости старых версий.

Перед переводом sunpole/uCode-Bench в PRIVATE следует перенести
публичные Releases и настроить публичный источник обновлений — это не часть
пилота. Старый sunpole/uCode пока не изменять.

## Для последующего агента

Не подменять историческую сборку исходниками текущего main; не подставлять
скриншоты нового UI под старые теги. Не считать действия GitHub Actions
стабильным публичным хранилищем. Не менять защищённый исходный HTML
и SHA256-договор UI. При отчёте отличать готовые файлы, успешные CI,
визуально принятые снимки и план публикации.
