# P04 + первый набор P05 — CPU и процессы

Этот отчёт фиксирует первый CPU-патч. Следующий рабочий набор добавляет thread backend, изолированную affinity, RAM budgets и серии: [RESOURCE_LAB.md](RESOURCE_LAB.md). Ограничения ниже относятся к исходному срезу, актуальные возможности указаны в новом отчёте.

Основа 6ca9e87 (P02), ветка codex/cpu-process-p04-p05. По просьбе пользователя выбран набор **15 пунктов**: P04.1–10 и P05.1,3,4,8,9. Это внутренний патч одного комплексного этапа. Ограничения ниже не объявляются выполненными функциями.

## Что видно и работает

Вкладка **CPU / RAM** и пункт **Настройки → CPU, RAM и диск** показывают модель CPU, физические ядра, логические CPU, доступные процессу ресурсы, processor groups, RAM и свободное место на диске PDF. Физические ядра и SMT-потоки не складываются.

Для обычной генерации доступны **Последовательно** и **Процессы**, произвольное допустимое число процессов и независимый размер партии 1–1000. Presets включают степени двойки, доступные физические ядра и логические CPU, без потолка 12/16/32. Число рабочих процессов ограничивается доступными CPU, числом партий и оценкой RAM. Например, 7 уникальных значений при партии 32 создают только одну рабочую задачу — для маленькой проверки двух процессов задайте партию 1. Это не выбор/закрепление конкретных ядер; исполнением управляет ОС.

Матрицы уникальных QR кодируются партиями в собственных spawn-процессах. На процесс одновременно отправляется одна партия; порядок возвращается к порядку TXT независимо от времени завершения. Экземпляры используют прежний кэш. Общий PDF, отдельные PDF и независимый QA пока выполняются последовательно в родительском процессе. Пул не является параллельным writer/merger.

Остановка опрашивается при запуске/между ответами; сигнал передаётся собственным worker. После ограниченного ожидания завершаются и join-ятся только созданные этим пулом Process-объекты. Падение процесса/закрытие канала — ошибка, а не успешный результат. Исходный TXT, старые запуски и частичные файлы сохраняются. Глобальная affinity/приоритеты/настройки Windows не меняются.

Предпочтения старой схемы v1/v2 получают defaults serial/1/32. Новые поля сохраняются вместе с прежними, старый API не стирает их. Большая научная методика/worker и gates не переведены на новый pool: исторические результаты остаются сопоставимыми внутри своего профиля.

## Определение аппаратных ресурсов

- Windows: CPU Sets, process default CPU sets, процессные группы и affinity mask для одной группы; имя/vendor читаются из аппаратной ветки registry без изменения. Для нескольких групп нельзя трактовать одну DWORD_PTR маску как весь компьютер. Резервированные другим процессам CPU исключаются. Парковка CPU не считается удалением ядра.
- Linux: online CPU/sysfs package/core и sched_getaffinity. Неизвестная топология оставляет физические ядра unknown, а не logical/2. CPU quota контейнера отличается от affinity и этим патчем не превращается в выдуманные ядра.
- RAM: GlobalMemoryStatusEx или /proc/meminfo с учётом доступных cgroup v2 memory.max/current по предкам. Резерв: max(512 МиБ, 10% доступной RAM). Оценка процесса: базовые 256 МиБ + 40000 байт на уникальное значение + 128 МиБ на фактически создаваемый worker. Это консервативная оценка, **не измеренный пик и не жёсткая RAM-квота**. При неизвестной RAM процессный режим отклоняется; последовательный сохраняется.
- Windows job memory/CPU limits, cgroup v1, индивидуальные ограничения потоков и полное назначение worker по processor groups пока не реализованы. Снимок содержит источник, reason и scope; неизвестное не становится подтверждённым ресурсом. Настоящий компьютер >64 CPU не проверялся; автоматическая модель — 144 логических, 72 физических в нескольких группах с ограниченным набором доступных CPU.
- Диск выбранной папки: свободные/общие байты. Windows использует read-only IOCTL_STORAGE_QUERY_PROPERTY для bus и seek penalty; Linux — доступный sysfs block/queue. No seek penalty/non-rotational может означать SSD или виртуальный накопитель, не доказательство физической модели. RAID/USB/overlay могут скрывать тип; тогда unknown с причиной.
- Кнопка **Проверить запись 32 КиБ** явно запускает небольшой write/flush/fsync в существующей выбранной папке. Временный файл принадлежит tempfile и закрывается; посторонние файлы не удаляются. Проверка доказывает возможность записи, не скорость диска. Автоматического теста диска нет.

В hardware-снимке нет имени компьютера, серийных номеров, аккаунтов и путей пользователя. Manifest дополнительно хранит execution: запрос/фактические workers, размер партии, PID собственных workers, завершённые значения, верхнюю наблюдаемую очередь и оценку RAM. В ОТЧЁТ.txt есть понятный раздел ресурсов. PID не нужны для публичного сравнения и могут быть исключены из очищенной сводки.

## Процессы, потоки и движки

| Способ | Применимость сейчас |
| --- | --- |
| ReportLab + последовательное исполнение | Рабочий прежний путь; не платит за spawn/IPC |
| ReportLab + spawn pool | Реализовано для QR encoding; импорт/запуск/передача/закрытие пула входят во время кодирования |
| Python threads | В CPython с GIL не ускоряют чистый Python CPU-bound код автоматически; полезны для I/O или совместимых native библиотек, освобождающих GIL. Backend ещё не подключён |
| PyMuPDF | Есть официальный multiprocessing-рецепт; многопоточная работа прямо не поддерживается. В текущем проекте это адаптер объединения, не новый QR generator |
| Один PDF из параллельных фрагментов | Потребует отдельной стратегии P06 и QA; этим патчем не подменяется прямой writer |

Собственный ограниченный pool не использует ProcessPoolExecutor с его Windows-ограничением 61 worker. Это не доказательство масштабирования до 144: такая топология проверена только моделью, реальная автоматическая работа — два процесса на малых данных.

Наличие «NVMe 3000+ МБ/с» не задаёт скорость uCode. По устройству текущего процесса CPU-кодирование/QA, spawn и работа с множеством маленьких файлов могут преобладать над передачей больших последовательных блоков. Это вывод из архитектуры, не измеренное сравнение SATA/NVMe. RAM становится критичной при росте числа процессов/буферов и вытеснении в файл подкачки. Этот патч не обосновывает покупку NVMe или конкретный обязательный объём RAM: сначала нужны пользовательские одинаковые прогоны по фазам. RAM/Disk/Hybrid и автоматический поиск лучшей конфигурации остаются P06/P08.

Первичные источники: [Python 3.12 threads/GIL](https://docs.python.org/3.12/library/threading.html), [multiprocessing](https://docs.python.org/3.12/library/multiprocessing.html), [ProcessPoolExecutor](https://docs.python.org/3.12/library/concurrent.futures.html), [PyMuPDF multiprocessing](https://pymupdf.readthedocs.io/en/latest/recipes-multiprocessing.html), [Windows CPU Sets](https://learn.microsoft.com/en-us/windows/win32/procthread/cpu-sets), [CPU Set structure](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-system_cpu_set_information), [process groups](https://learn.microsoft.com/en-us/windows/win32/api/processtopologyapi/nf-processtopologyapi-getprocessgroupaffinity), [storage descriptor](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ns-winioctl-storage_device_descriptor), [seek penalty](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ns-winioctl-device_seek_penalty_descriptor).
