# Комплексная модернизация uCode — карта патчей

Основание: e51e2eb, актуальная v0.2, PR #2. Новое задание: [MODERNIZATION_SPEC.md](MODERNIZATION_SPEC.md), SHA-256 фиксируется в WORK_LOG. Это один комплексный этап, а не отдельные релизы. В каждом активном патче не более 15 небольших задач. Завершение одного патча не означает завершение всего ТЗ.

## Правила выполнения и приёмки

- Реализовывать последовательно по зависимостям; сохранять рабочие QR, геометрию, CMYK, независимый QA и старые результаты.
- Визуальные проверки выполняет пользователь: не делать ручные обходы мышью и скриншоты. Это осознанная граница нового ТЗ, а не блокирующий долг автоматизации.
- Автоматически проверять небольшие реальные PDF и контролируемые модели. Нагрузки 200/1000/10000 и тяжёлые матрицы запускает пользователь из программы. Прежнее разрешение автоматических больших прогонов больше не применяется.
- Не повышать лимиты до внедрения ограниченных буферов, оценки ресурсов и отмены. Недоступные режимы отключать с причиной, без подмены.
- Старый научный профиль (QR V1-M, K100, 3 повтора, gate 200→1000) хранить как воспроизводимый профиль. Новая настраиваемая лаборатория должна иметь отдельную схему параметров и явно описанное полное время.
- Не подключать линейные коды из соседнего sunpole/uCode без отдельного переноса: в текущем репозитории реально работает QR; другие пункты меню пока заглушки. Квадратный QR не означает Data Matrix.
- Статусы: TODO, ACTIVE, VERIFIED, LIMITATION, USER-CHECK. VERIFIED требует команды/артефакта и свежего результата. У каждого патча отдельный коммит и отчёт; публичная копия через PR, main не менять.

## P01 — реальная модульность и достоверные счётчики (10 задач)

Статус: VERIFIED локально и [Windows/Linux CI](https://github.com/sunpole/uCode-Bench/actions/runs/40576709327); 108 тестов (локально 107 PASS / 1 SKIPPED, CI 103 PASS / 5 SKIPPED) и настоящие PDF 2/7. PR #3. Ветка codex/modernization-p01. Зависимости: существующая v0.2. Все 10 задач реализованы; границы приёмки и артефакты в [MODERNIZATION_P01.md](MODERNIZATION_P01.md).

1. Сохранить новое ТЗ, аудит и карту всех долгов/патчей.
2. Ввести реестр движков генерации отдельно от типов кодов и движков объединения.
3. Объявлять реальные возможности и точную версию текущего ReportLab; ничего не устанавливать.
4. Подключить production pipeline через выбранный модуль кода и движок, включая валидацию настроек и независимый QA.
5. Проверять совместимость до создания результатов; сверять порядок закодированных значений с TXT.
6. Перевести исторические worker encode/direct/singles на тот же текущий движок, сохраняя границы таймера.
7. Разделить текущую скорость по короткому окну и среднюю скорость этапа; проверить сброс между повторами.
8. Показывать фактический движок/версию и сохранять их в PDF-отчётах; пояснить отсутствие callback у merger.
9. Заменить автоматический CI 200/1000/10000 небольшим реальным smoke; большие скрипты оставить для явного запуска.
10. Добавить контрактные/регрессионные проверки, проверить интегрированное состояние, обновить README/CONTRACTS/WORK_LOG.

Приёмка: смена зарегистрированного движка проходит через весь production pipeline без его редактирования; неизвестный/несовместимый движок не создаёт каталог; ошибки входного порядка обнаруживаются; настоящий небольшой PDF проходит прежний QA. Большие нагрузки и визуальные проверки не выполняются.

## P04 — оборудование, топология и выбор ресурсов (10 задач)

Реализован первый аппаратный снимок и UI в codex/cpu-process-p04-p05: Windows CPU Sets/groups/process mask, Linux sysfs/affinity, RAM, диск/unknown и ручной write probe. Малые проверки VERIFIED локально и [Windows/Linux CI](https://github.com/sunpole/uCode-Bench/actions/runs/40633332965), PR #5: 129 тестов на ОС (124 PASS / 5 необязательных SKIPPED), 12 малых PDF сценариев на двух ОС, QA PASS. **Ограничения:** нет полного учёта job/cgroup v1 quotas и индивидуальных thread/group masks; >64 CPU проверены моделью, не реальным сервером. Эти границы остаются LIMITATION, весь P04 не объявляется универсальным определением любых ограничений ОС. Подробности: [MODERNIZATION_CPU.md](MODERNIZATION_CPU.md). Требования 4, 5, 11.

1. Модель аппаратного снимка с unknown/reason и источником каждого поля.
2. Модель/производитель CPU, физические ядра, логические CPU и SMT без двойного подсчёта.
3. Доступные ресурсы процесса, affinity и Windows processor groups >64.
4. Динамические допустимые presets и произвольное число без потолка 12/16/32.
5. Linux fallback и контроль недостоверных/неполных сведений.
6. Общая/доступная RAM и безопасный резерв, без изменения ОС.
7. Диск выбранной папки, свободное место, write probe в собственной временной папке.
8. Тип носителя/шина только при надёжном источнике; неизвестное не объявлять NVMe.
9. Снимок при запуске, отображение в программе, очищенная схема отчёта без серийников/личных путей.
10. Модели 1/36/64+ ядер, ограниченных групп/affinity и неизвестного диска в автоматических тестах.

## P05 — управление исполнением и CPU (9 задач)

Набор лаборатории проверен: [PR #6](https://github.com/sunpole/uCode-Bench/pull/6), [Windows/Linux CI](https://github.com/sunpole/uCode-Bench/actions/runs/40639361409), 142 теста на ОС (137 PASS /5 необязательных SKIPPED), 36 настоящих двухстраничных лабораторных PDF с QA PASS. Крупные пользовательские матрицы и перечисленные ограничения остаются открытыми.

Первый набор 1,3,4,8,9 реализован для QR encode; [новый набор лаборатории](RESOURCE_LAB.md) добавляет 2 (ThreadPoolExecutor), принудительную affinity отдельной попытки, physical/logical/all/all-2 и динамические workers. CPU mask подтверждается ОС и наследуется worker. **Ограничения 5–7:** Windows multi-group affinity SKIPPED, нет закрепления каждого worker за отдельным ядром или автоматического выбора быстрее всех для production. Linux поддерживает доступные CPU через affinity без потолка 12/16/32. Запись PDF/QA пока последовательны, полный поток RAM не заявляется. Функциональные малые проверки выполнены; большие матрицы — USER-CHECK. Требования 5, часть 8.1.

1. Serial backend с общим контрактом заданий/результатов.
2. Thread backend только для совместимых движков; ограничения GIL показывать явно.
3. Process pool с ограниченным числом задач и стабильным порядком результатов.
4. Размер партии и число workers отдельно от выбранных CPU.
5. Auto scheduler и affinity только собственных worker, без глобального планировщика.
6. Физические/логические CPU по реальной топологии и группам.
7. Auto/max режимы без обязательного резерва фиксированных ядер.
8. Безопасная отмена/завершение собственного дерева задач, сохранение частичных результатов.
9. Малые тесты порядка, эквивалентности, ограничений, отказов и отмены на всех backend.
