# uCode — комплексная модернизация генератора и лаборатории производительности

## Роли

Работай как команда специалистов:

- Senior Software Architect — архитектура и модульность.
- Senior Performance Engineer — производительность CPU, RAM, SSD/NVMe, параллельная обработка.
- PDF/Barcode Engineer — создание кодов, PDF, корректность печатных параметров.
- Benchmark/QA Engineer — достоверность измерений и автоматические проверки.
- Senior UI/UX Designer — современный компактный интерфейс.
- Windows Engineer — определение характеристик оборудования и управление вычислительными ресурсами.

## Главная цель

Превратить существующий проект uCode в профессиональный, максимально быстрый и гибко настраиваемый генератор кодов с полноценной системой сравнительного тестирования на разных компьютерах.

Программа должна автоматически определять возможности текущего ПК и позволять пользователю экспериментально находить наиболее производительное сочетание:

**Движок генерации × CPU × физические ядра × логические потоки × распределение процессов × RAM × диск × способ формирования PDF × количество кодов × повторы.**

Приоритеты:

1. Максимальная реальная производительность.
2. Корректность созданных кодов и PDF.
3. Достоверность и воспроизводимость тестов.
4. Стабильность и безопасность использования ресурсов.
5. Максимальная настраиваемость.
6. Компактный, современный, понятный UI/UX.
7. Минимальные накладные расходы интерфейса.
8. Экономное использование времени разработки и токенов Codex.

Реализовать все требования в рамках **одного комплексного этапа разработки**, без искусственного разделения на отдельные релизы.

Внутреннюю реализацию организовать модульно, чтобы ошибки и новые функции можно было сопровождать независимо.

Не переписывать работающий код без технической необходимости.

# 2. Обычная генерация кодов

Пользователь должен иметь возможность независимо настраивать обычное создание кодов и проведение тестирования.

Предусмотреть:

- Выбор типа кодов.
- Выбор движка.
- Выбор количества уникальных значений.
- Выбор количества экземпляров каждого значения.
- Размеры кодов.
- Цветовые настройки.
- Параметры PDF.
- Папку сохранения.
- Способ генерации и обработки данных.
- Вычислительные ресурсы.

Сохранить имеющиеся виды кодов, включая QR и существующие линейные штрихкоды.

Проверить поддержку Data Matrix, EAN-13 и других предусмотренных проектом типов, включая запрос на квадратные коды. Не подменять один стандарт другим без подтверждения.

Архитектура должна позволять подключать дополнительные виды кодов.

Сохранить встроенный генератор исходной базы данных с быстрыми пресетами:

**200 / 1 000 / 10 000**, а также произвольное количество.

Сохранить и улучшить импорт TXT:

- Понятный выбор файла.
- Проверка кодировки.
- Проверка содержимого.
- Отображение количества записей.
- Обработка некорректных данных.
- Возможность работы с большими файлами без обязательной полной загрузки в память.

## 2.1. Подсчёт кодов

Принятая формула для одного вида кода:

Количество создаваемых кодов = количество уникальных значений × количество экземпляров каждого значения.

Если выбрано несколько типов кодов, отдельно показывать количество для каждого типа и общий итог.

**Повторные тесты и количество тестовых конфигураций учитывать отдельно**, не смешивая их с количеством кодов в одном запуске.

Например:

200 уникальных значений × 3 экземпляра = 600 кодов одного выбранного типа.

Три повторных теста означают три отдельных запуска с соответствующими измерениями.

# 4. Определение оборудования

При запуске программы автоматически определять характеристики доступной вычислительной системы.

## CPU

Определять:

- Производителя и модель.
- Количество физических ядер.
- Количество логических процессоров.
- Наличие SMT/Hyper-Threading.
- Доступные Windows процессорные ресурсы.
- Ограничения на привязку процессов и потоков.
- Прочие характеристики, полезные для измерений, если доступны.

**Не устанавливать искусственный максимальный предел в 12, 16 или 32 ядра.**

Если на ПК 36, 64 или больше физических ядер, программа должна определять их и предлагать доступные варианты.

Учитывать особенности Windows при количестве логических процессоров более 64, включая процессорные группы, если это требуется.

## RAM

Определять:

- Общий объём ОЗУ.
- Доступную физическую память.
- Текущее использование.
- Примерный безопасный объём для рабочих буферов.
- Возможность использования оперативной памяти для промежуточных результатов.

Если данные о типе или скорости памяти доступны надёжным способом, включать их в характеристики компьютера.

## Накопители

Определять для выбранных папок:

- Диск назначения.
- Тип носителя, если определяется достоверно.
- SATA SSD / NVMe SSD / HDD / другой.
- Доступное место.
- Возможность записи.
- Предполагаемую нагрузку по записи.

Не считать NVMe автоматически быстрее SATA во всех сценариях.

Для сравнения производительности использовать реальные результаты тестов конкретного накопителя.

Если требуется отдельный тест скорости диска, выполнять его контролируемо, с ограничением размера временных данных и последующей очисткой.

Не путать заявленную последовательную скорость SSD с реальной скоростью генерации PDF.

- 1 ядро/поток.
- 2.
- 4.

Если доступно 36 или более ядер, позволить использовать любое допустимое количество вплоть до максимума.

## 5.1. Физические и логические ресурсы

Предусмотреть сравнение:

1. Использование выбранного количества физических ядер.
2. Использование выбранного количества логических процессоров.
3. Использование максимума доступных логических процессоров.
4. Автоматическое распределение средствами Windows.
5. Контролируемое закрепление рабочих процессов/потоков за CPU (affinity).

Физические ядра и логические потоки не являются независимыми суммируемыми ресурсами.

Реализовать корректную модель, учитывающую топологию процессора и не допускающую двойного подсчёта.

## 5.2. Методы параллельной обработки

Исследовать и реализовать подходящие способы:

- Однопроцессная генерация.
- Многопоточная обработка.
- Многопроцессная обработка.
- Пулы рабочих процессов.
- Пакетная обработка.
- Автоматический выбор параллелизма.

Учитывать технические ограничения текущего языка программирования и библиотек, включая возможные ограничения реального параллельного выполнения CPU-bound операций.

Количество рабочих задач и их привязка к CPU должны настраиваться отдельно, если это позволяет архитектура.

Не резервировать принудительно 1–4 ядра для Windows без необходимости.

Предусмотреть автоматический безопасный режим и вариант использования максимума доступных ресурсов.

Не изменять глобальные настройки планировщика Windows.

# 6. Режимы использования CPU, RAM и диска

Это отдельный важный модуль.

Нужно исследовать, какие архитектуры обработки данных реально обеспечивают максимальную скорость.

Предусмотреть совместимые стратегии:

**A. CPU + потоковая обработка**

Генерация кодов небольшими порциями, без накопления всей базы в ОЗУ.

**B. RAM-first**

Создание и временное накопление промежуточных данных в оперативной памяти, если её достаточно.

**C. Disk-first**

Использование временных файлов на выбранном диске, чтобы не хранить все промежуточные данные в RAM.

**D. Hybrid RAM + Disk**

Часть обработки в RAM, автоматический перенос промежуточных данных на диск при достижении заданного порога.

**E. Auto**

Автоматический выбор стратегии на основании объёма памяти, свободного места, характеристик текущего ПК и результатов ранее проведённых измерений.

CPU в любом из этих вариантов остаётся необходимым вычислительным ресурсом. Различаются способы размещения данных и организация обработки.

## Настройки памяти

Позволить выбирать:

- Автоматический лимит RAM.
- Пользовательский лимит в МБ/ГБ.
- Долю доступной оперативной памяти.
- Режим максимального безопасного использования RAM.

Даже в максимальном режиме оставлять резерв памяти для Windows и других процессов.

Не допускать неконтролируемого исчерпания ОЗУ и зависания компьютера.

При нехватке памяти предусмотреть корректное снижение объёма буферов или переключение на допустимую дисковую стратегию.

## Настройки диска

Отдельно выбирать:

- Папку временных данных.
- Папку окончательных PDF.
- Накопитель для тестирования.
- Максимальный объём временных данных.

Позволять сравнивать работу с SATA SSD и NVMe на одном компьютере, если такие накопители доступны.

Проверять наличие дисков и свободного места перед запуском.

# 7. Контроль свободного места

Перед каждой генерацией и серией тестов рассчитывать прогнозируемый объём результатов.

Учитывать:

- Количество уникальных кодов.
- Количество экземпляров.
- Выбранные типы кодов.
- Размеры и параметры кодов.
- Выбранную структуру PDF.
- Количество отдельных файлов.
- Необходимые временные данные.
- Режим сохранения результатов тестов.

Расчёт может быть приблизительным, но метод должен быть понятным.

Для уточнения оценки можно использовать короткую калибровочную генерацию типового набора.

Показывать:

- Прогнозируемый объём данных.
- Доступное место.
- Примерный необходимый резерв.
- Предупреждение о возможной нехватке места.

При заведомой нехватке места не запускать операцию, обречённую на ошибку.

# 8. Полная лаборатория тестирования

Создать единый модуль **«Тесты»**.

Все тесты должны открываться из одной компактной кнопки с вложенным меню внутри главного окна.

Сохранить готовые нагрузки:

- 200 кодов.
- 1 000 кодов.
- 10 000 кодов.

Также добавить произвольное количество.

Пользователь должен самостоятельно выбирать тесты, комбинации параметров и число повторов.

## 8.1. Перекрёстная матрица тестирования

Создать конструктор тестовой матрицы.

Оси сравнения:

1. Тип кода.
2. Движок генерации.
3. Количество кодов.
4. Количество экземпляров.
5. Количество физических ядер или логических процессоров.
6. Количество рабочих потоков/процессов.
7. Режим распределения нагрузки CPU.
8. Режим работы с RAM.
9. Лимит используемой RAM.
10. Режим работы с диском.
11. Выбранный накопитель.
12. Метод формирования PDF.
13. Режим сохранения PDF.
14. Количество повторов.
15. Режим интерфейса.

Пользователь должен иметь возможность включать любую доступную комбинацию поддерживаемых параметров.

Реализовать режимы:

- Один выбранный тест.
- Сравнение одного параметра.
- Выборочная матрица.
- Полная матрица доступных сочетаний.

При несовместимости параметров конкретный сценарий пропускать с объяснением причины.

**Не запускать автоматически все возможные сочетания.**

Сначала рассчитывать количество тестовых запусков, примерный объём файлов и ожидаемую длительность на основании короткой калибровки, если она доступна.

Показывать объём запланированной работы до старта.

При необходимости пользователь должен иметь возможность сократить матрицу, сохранив исходные настройки остальных параметров.

## 8.2. Повторные испытания

Добавить:

- Настраиваемое число повторов.
- Предварительный прогрев перед измерениями.
- Фиксацию результата каждого повтора.
- Минимальное время.
- Максимальное время.
- Среднее время.
- Медиану.
- Среднюю пропускную способность.
- Разброс результатов.

Прогрев не включать в измеряемые повторы.

Разделять случайные системные задержки и устойчивые отличия производительности.

Для длительных серий желательно предусмотреть возможность остановки и корректного сохранения уже завершённых результатов.

## 8.3. Точная методология времени

Главная измеряемая величина:

**Полное время от начала создания кодов до завершения формирования и сохранения итогового PDF на диск.**

Измерять весь рабочий цикл.

Дополнительно, если возможно без существенного замедления, фиксировать время отдельных фаз:

- Подготовка данных.
- Генерация кодов.
- Формирование PDF.
- Объединение PDF.
- Запись и завершение сохранения.

Чётко документировать, входит ли синхронизация файловых данных на накопитель в измерение.

Использовать высокоточный монотонный таймер.

Не подменять реальное измерение предположениями или расчётными скоростями.

## 8.4. Достоверность

Все сравниваемые конфигурации должны использовать:

- Одинаковые входные данные.
- Одинаковые размеры кодов.
- Одинаковую цветовую модель.
- Одинаковые требования к PDF.
- Одинаковое количество результатов.
- Одинаковый порядок измерения времени.
- Одинаковые условия сохранения файлов.

Если варианты создают функционально разные результаты, не объявлять их напрямую сопоставимыми.

Учитывать влияние кэширования, фоновой нагрузки Windows, состояния накопителя и других факторов.

Не создавать искусственные преимущества отдельным движкам.

- Совместимость с текущей архитектурой.

Добавить сравнительные тесты движков на одинаковых исходных данных и эквивалентных PDF-результатах.

# 10. График скорости

Добавить **один совмещённый график с несколькими шкалами**.

Необходимо показывать:

- Изменение скорости генерации в кодах/с.
- Прошедшее время.
- Накопленное количество созданных кодов.
- Общее запланированное количество.
- Процент выполнения.
- Пики и падения скорости.

Предлагаемая реализация:

- Горизонтальная ось — прошедшее время.
- Левая вертикальная шкала — скорость в кодах/с.
- Правая вертикальная шкала — количество готовых кодов.
- Основная кривая — изменение скорости.
- Дополнительная кривая — накопленный прогресс.
- Линия цели — запланированное количество кодов.

Числовые показатели времени, процентов, средней, максимальной и минимальной скорости разместить компактно возле графика.

Важное условие:

**График не должен уменьшать производительность генератора.**

Собирать данные с минимальными накладными расходами.

Обновлять изображение графика с ограниченной частотой, независимо от количества создаваемых кодов.

Не выполнять перерисовку после каждого кода.

Сохранять данные измерений для последующего анализа и просмотра графика после теста.

# 11. Отчёты и сравнение компьютеров

Создать систему сохранения результатов тестирования.

Каждый тест должен иметь уникальный идентификатор.

В отчёте фиксировать:

## Компьютер

- Модель CPU.
- Физические ядра.
- Логические процессоры.
- Доступную RAM.
- Характеристики накопителя.
- Версию Windows.
- Архитектуру системы.
- Версию uCode.

## Параметры теста

- Тип кода.
- Движок и его версия.
- Количество кодов и экземпляров.
- Количество рабочих процессов/потоков.
- Выбранные ядра.
- Affinity или автоматическое распределение.
- Режим RAM.
- Лимиты RAM.
- Используемый диск.
- Способ формирования PDF.
- Настройки PDF.
- Количество повторов.
- Режим интерфейса.

## Результаты

- Полное время.
- Кодов/с.
- Лучшее и худшее время.
- Среднее время.
- Медиана.
- Разброс.
- Максимальная и минимальная наблюдаемая скорость.
- Размер итоговых файлов.
- Успешность выполнения.
- Ошибки и предупреждения.

Предусмотреть удобное отображение результатов внутри программы.

Дополнительно сохранять машинно-читаемые данные, например JSON/CSV, и понятный человеку итоговый отчёт.

Форматы выбирать с учётом простоты реализации и надёжности.

## Сравнительная аналитика

Позволить загрузить результаты разных запусков и разных компьютеров.

Например:

- Домашний Xeon с SATA SSD.
- Сервер с большим количеством ядер и RAM.
- Рабочий ПК с высокочастотным CPU, DDR5 и быстрым NVMe.

Показывать:

- Какая конфигурация быстрее.
- На сколько процентов.
- Во сколько раз.
- Разницу по времени.
- Разницу по кодам/с.
- Наиболее результативный движок.
- Наиболее эффективное число рабочих процессов.
- Лучший протестированный способ использования RAM и диска.

Формировать итоговый рейтинг **только среди реально протестированных сопоставимых конфигураций**.

Не объявлять один движок или метод универсально лучшим для всех компьютеров.

Не собирать и не публиковать серийные номера оборудования, личные пути пользователя и другую ненужную конфиденциальную информацию.

# 12. Режим «Минимум»

Добавить два варианта минимального режима.

**Минимум A — компактный контроль**

Оставить только наиболее необходимые элементы:

- Название операции.
- Минимальный прогресс.
- Возможность остановки.

Отключить график, анимации и частые обновления интерфейса.

**Минимум B — максимальная производительность**

Во время генерации максимально отключать необязательную работу интерфейса, включая графики и визуальные счётчики.

Оставить безопасный способ остановить операцию.

В обоих режимах продолжать сбор необходимых метрик без постоянной отрисовки.

Итоговые данные отчёта должны быть такими же полными, как в обычном режиме.

Включить режим интерфейса в параметры сравнительных тестов, чтобы проверить, влияет ли графика на реальную скорость.
