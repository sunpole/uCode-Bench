Это нагрузка процессов uCode, а не общая загрузка Windows; мгновенные пики и короткие процессы могли быть пропущены.

Таким образом, на этапе QR параллелизм уже работает, а этап записи PDF оставляет значительную часть CPU свободной. Новый конвейер позволяет проверить другой способ перекрытия этих этапов. ## Следующий короткий тест: 12 результатов

В **Тесты → Консоль** вставить две строки, нажать **Проверить**, затем запустить:

```text
test lab --codes 10000 --unit cores --cpu 13 --backend process --repeats 3 --warmups 0 --batch 32 --files multipage --pdf compact --activity minimal --ram max --metrics off --qa off --xy on
test pipeline --codes 10000 --split cores:12+2,smt:24+4,smt:28+0 --schedule queue --batch 32 --repeats 3 --pdf compact --ram max --metrics off --qa off --xy on
```

Первая строка — 3 повтора схемы QR, затем PDF. Вторая — 9 повторов трёх конвейерных вариантов. Всего 12 результатов. Сбор CPU выключен, запись XY включена, проверка PDF выключена. На этом ПК 14 ядер/28 SMT достаточно для этих наборов. Скорость заранее не обещается. Большой запуск выполняет пользователь, автоматическая проверка ограничивается планом.

После запуска открыть отчёт → **XY: ход работы** → выбрать повтор и этап. Для разбора можно прислать commands.html либо JSON очереди. Для проверки качества заменить --qa off на --qa full.

Для оценки расходов записи XY: две одинаковые команды, у первой --xy off, у второй --xy on. Для расходов CPU-диагностики: --metrics off,cpu при фиксированном XY. На другом компьютере сначала проверить доступные ядра в программе и плане.
