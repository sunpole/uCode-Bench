# Лаборатория CPU / RAM — первый рабочий конструктор серии

Основа 14f8542 (первый CPU-патч), ветка codex/resource-lab-p05-p08. Один комплексный этап, выбранный набор **15 небольших задач**, без новых зависимостей. Уточнение пользователя: максимум RAM означает полезные QR/PDF-данные с безопасным резервом ОС; искусственного заполнения памяти нет.

## Как пользоваться

Перезапустите Start-uCode.cmd из текущей тестовой копии, откройте **Лаборатория** или **Тесты → Лаборатория CPU / RAM**.

1. **Кодов:** например `200` для первого сравнения либо `200,500,1000,10000` для серии. Кнопка с размерами заполняет список и ничего не запускает. Принимаются любые целые 1–10000; текущий лимит не увеличен.
2. **CPU:** `1,2,4,6,12,all-2,all`. Можно ввести своё число без потолка 12/16/32. `all`/`все` — весь доступный выбранный ресурс, `all-2`/`все-2` — на два меньше. Отдельно выбираются логические CPU, физические ядра (один SMT-поток на ядро) или оба варианта.
3. **Методы:** русские названия из формы либо `serial,process,thread`. Это способы выполнения кодирования текущим ReportLab, не три разных QR/PDF-движка. Запись PDF и QA пока последовательны.
4. **RAM:** `auto`, `50%`, `80%`, `max` либо, например, `4096MiB`. Это бюджеты полезной обработки. Фактическое потребление измеряется отдельно.
5. По умолчанию **3 повтора**, без прогрева. Можно задать 0–3 прогрева, которые исключаются из статистики; для небольших функциональных проверок допустим 1 повтор. Партия — 1–1000, workers — 0 (по числу выбранных CPU) или отдельное положительное число. CPU mask и число workers — разные параметры.
6. **Первый вариант** выполняет первые значения каждого списка с заданными повторами. **Вся выбранная серия** выполняет выбранное декартово произведение **по очереди**, не создавая одновременных конкурирующих тестов.
7. Видны число конфигураций/реальных запусков, SKIPPED и консервативная оценка места. Время без калибровки не выдумывается. Недоступные CPU и совпадающие маски в одной единице CPU получают SKIPPED с причиной/ссылкой на эквивалентный вариант. Например, на 14 физических ядрах `12` и `all-2` не нужно измерять дважды.
8. Отмена сохраняет выполненные и частичные результаты. **Посмотреть отчёт** открывает comparison.html; рядом ОТЧЁТ.txt, comparison.csv, lab.json и настоящие PDF. **Тесты → Результаты лаборатории** открывает историю папок. Списки формы сохраняются проектно в .local-state/lab-settings.json; старые результаты не заменяются.

Формат PDF, размер, поле и CMYK берутся из текущих настроек главного окна и фиксируются на серию. Результаты GUI сохраняются в выбранной **Папке PDF / laboratory/**; так можно выбрать другой накопитель. CLI по умолчанию использует output/laboratory/, smoke — output/lab-smoke/. Тестовые значения последовательные и уникальные, поэтому кэш экземпляров не подменяет сравнение уникального кодирования. Пользовательский TXT и ось экземпляров в эту первую матрицу не входят.

## Что означает «все ядра»

На обнаруженном ранее Xeon E5-2680 v4: 14 физических / 28 логических CPU. Для физического режима `all` означает 14 выбранных логических представителей разных ядер, `all-2` — 12. Для логического режима это 28 и 26. Ресурсы каждый раз определяются заново на текущем компьютере, эти числа не зашиты в приложение.

Каждая попытка запускается в отдельном Python-процессе. Только он получает принудительную affinity; его worker/renderer наследуют ограничения. GUI и чужие процессы не ограничиваются. Выбранные ID сверяются с ОС после применения, для process backend проверяется и наследование workers. Linux affinity применяется к существующим собственным потокам; последующие потоки создаются после ограничения. В Windows используется SetProcessAffinityMask для одной processor group. **Принудительная Windows affinity нескольких processor groups пока SKIPPED**, а не фиктивное использование >64 CPU. Linux допускает доступные ОС CPU без такого численного потолка. Неизвестная топология не превращается в физические ядра logical/2.

«Все − 2» исключает два выбранных ресурса из маски теста. Это **не эксклюзивная резервация** для Windows: другие программы могут использовать любые разрешённые им CPU, включая выбранные тестом. Максимальная доступность CPU не гарантирует 100% загрузку: конечный объём работы, spawn/IPC, последовательные PDF и QA остаются ограничениями. Эффективный размер пула не больше числа партий и явно записывается в отчёт.

## Способы распределения

| Метод | Реальная реализация | Что сравнивается |
| --- | --- | --- |
| serial | Прежний прямой вызов encoder | База без пула |
| process | Собственный spawn pool, одна партия в полёте на worker | Настоящее CPU-параллельное кодирование с сохранением порядка; запуск/импорты/IPC/закрытие включены во время encoder |
| thread | ThreadPoolExecutor с ограниченной очередью | Только независимые ReportLab QR-матрицы; PDF canvas не разделяется между потоками. В обычном CPython действует GIL, ускорение не обещается |

ProcessPoolExecutor, joblib, Ray/Dask и дополнительные QR/PDF-движки не установлены и не объявляются реализованными. Другие generation engines — P03; текущие mergers — отдельная историческая задача. Ограниченный IPC не означает потоковую RAM всего тиража: до 10000 матриц остаются в памяти, Disk/Hybrid/spill пока нет.

## RAM: бюджет и реальное потребление

При доступной памяти F резерв равен max(1 ГиБ, 10% F), безопасный максимум — F минус резерв. `max` разрешает этот максимум; `auto` и `80%` — 80% безопасного максимума; `50%` — половину. Например, при 11 ГиБ свободных резерв 1,1 ГиБ, max budget около 9,9 ГиБ. Значения пересчитываются перед каждой попыткой. Это не обязательное выделение такого объёма.

Прежде чем выполнять генерацию, выбранный бюджет сравнивается с прежней консервативной оценкой: базовые 256 МиБ + данные + 128 МиБ на фактический process worker или 8 МиБ на thread worker. Оценка не является измеренным пиком. Слишком маленький бюджет получает SKIPPED; размер пула не уменьшается незаметно. Неизвестная доступная RAM не разрешает фиктивный max.

- Windows: собственный вложенный Job Object ограничивает суммарный commit дерева теста выбранным бюджетом, KILL_ON_JOB_CLOSE удерживает владение дочерними процессами. Если job недоступен из-за ограничений ОС/внешнего job, вариант SKIPPED. Это не изменение глобальных настроек памяти.
- Linux: наблюдаемый суммарный RSS и кооперативная отмена, без записи в системные cgroups и без kernel RAM quota. Различие механизмов записывается в raw trial, не маскируется как одинаковая жёсткая квота.
- Монитор примерно каждые 50 мс читает **одновременную сумму RSS собственного дерева** и доступную RAM. Превышение бюджета/исчерпание резерва отменяет попытку со статусом RESOURCE_LIMIT; результат не ранжируется. RSS может повторно учитывать общие страницы, короткие пики могут быть пропущены. В Windows дополнительно сохраняется наблюдаемый private bytes. Это не сумма индивидуальных исторических пиков.
- Сохраняются sample count, интервал, максимальное видимое число процессов и наблюдённые CPU seconds. Короткоживущие процессы могут уйти между измерениями; эти CPU seconds не выдаются за полный точный CPU time.

На 1000/10000 простых QR часто не нужно всё доступное ОЗУ. Если полезных данных меньше бюджета, память остаётся свободной; 50%, auto и max могут фактически использовать одинаково мало RAM. Эти режимы пока меняют **допуск/ограничение**, а не алгоритм хранения. Для полезного увеличения буферов/размера задач и переноса на диск нужны оставшиеся P06 RAM/Disk/Hybrid, а не пустое заполнение памяти.

## Методика времени, статистики и рекомендаций

Каждый повтор — новый изолированный процесс и отдельная папка с request, worker.log, trial.json, входным TXT, manifest, QA и PDF. Настройки, аппаратный снимок, Python/GIL, версия ReportLab и SHA-256 исходников фиксируются. Изменившиеся исходники/версия движка во время серии делают попытку ошибочной. Личные пути остаются только в локальных raw evidence; публичная сводка очищается.

`production_until_pdf_closed` — **реально измеренный wall clock** производственной части до начала QA: копии TXT, QR, закрытие всех выбранных PDF и фиксация файлов/хешей. Это не сумма фаз. Отдельно измеряются encoder, singles, multipage и QA. `total_including_qa` — полная партия с QA; `launcher_wall` — вся изолированная оболочка от Popen до завершения, включая старты/импорты/preflight/мониторинг/отчёты. Время encode включает его собственные pool spawn/import/IPC. Мониторинг включён во время всех новых наблюдаемых методов. Запись PDF закрывает файлы через прежний writer/ОС-кэш; **fsync PDF и физическая долговечность записи не заявляются**.

Для полного успешного набора повторов: min/max/mean/median/spread, кодов/с, пиковый наблюдаемый RSS. Прогрев исключается. Любая INVALID/ERROR/RESOURCE_LIMIT/CANCELLED/LIMITED или нехватка повторов исключает вариант из рекомендаций. Если нет успешных конфигураций, победитель не назначается.

Основной рейтинг — медиана партии **с QA**, старт контрольной изолированной оболочки показывается отдельно. Ускорение считается только при реально измеренной serial-базе на одном CPU для того же размера/RAM/unit/PDF-профиля; без базы — прочерк. Есть рекомендации по каждому размеру для всех RAM-политик и отдельно по RAM. Зелёным отмечен самый быстрый успешный вариант. Дополнительно выбирается меньше CPU, а при равенстве — меньший разрешённый RAM budget среди вариантов не дальше 5% от лучшей медианы. **5% — открытая эвристика удобства, не проверка статистической значимости.** Микроскопические различия и тест на двух кодах нельзя переносить на 1000 или другой ПК.

TXT объясняет расчёт и ошибки, HTML содержит компактную основную таблицу и раскрываемые полные фазы, CSV включает аппаратные/программные признаки для сравнения будущих компьютеров. В raw trial остаются точные CPU ID, RAM budget/guard, метрики, статус и пути к файлам. График, импорт нескольких историй с автоматическим общим рейтингом и полноценная ось PDF/engine/type пока остаются следующими задачами.

## Практический порядок сравнения

1. На своём ПК сначала один размер 200 или 1000, один RAM auto, serial/process; CPU 1/2/4/6/12/all-2/all. Это покажет, окупается ли пул. Для 14/28 логических отдельно полезно сравнить 14 (один поток на физическое ядро) и 28 (SMT).
2. Добавить thread как контроль GIL; не ожидать автоматически ускорения CPU-bound Python.
3. Для нескольких удачных CPU-вариантов сравнить 50%/auto/max и **фактический** RSS. Больший разрешённый бюджет сам по себе не ускоряет одинаковый алгоритм.
4. Затем 500/1000/10000 и нужные PDF-режимы. Все выбранные комбинации одной кнопкой возможны, но число запусков умножается на оси/повторы; проверить preview и место. Старые результаты не удаляются.

Это стартовая схема поиска, а не уже измеренная рекомендация «12 быстрее 28». Замена SATA на NVMe 3000+ не является требованием: влияние накопителя измеряется отдельно на одинаковых данных, с тем же профилем и правилами ОС-кэша.

## Набор 15 задач и проверки

1. Доступные CPU ID и реальная топология.
2. Числа/all/all-2 для physical/logical без двойного подсчёта SMT.
3. Изолированная принудительная affinity, подтверждение и наследование.
4. Третий backend ThreadPoolExecutor только для QR encode.
5. Максимальный безопасный/долевой/явный RAM budget для полезных данных.
6. Windows job и Linux cooperative guard собственного дерева.
7. Измерение RSS/наблюдаемых CPU seconds и сохранение области метрик.
8. План допустимой матрицы, эквивалентные маски, оценка диска.
9. Произвольные counts 1–10000, повторы/прогрев/партия/workers.
10. Последовательная очередь, отмена и сохранение частичных артефактов.
11. Фактический общий таймер до QA, отдельная оболочка, fingerprint.
12. Статистика, serial1 baseline и рекомендации только по успешным повторам.
13. Понятные TXT/HTML/CSV и raw trial.
14. Компактная вкладка, первый вариант/вся серия, история и предпочтения.
15. Малые реальные регрессии/CI, документация, PR и локальный архив.
