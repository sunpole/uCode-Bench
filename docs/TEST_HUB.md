## Пользовательский контракт

В главном окне одна вкладка **Тесты** с разделами **CPU/RAM**, **Конвейер**, **Подбор ПК**, **Научный**, **Консоль**, **Архив**, **История**. Основные действия доступны без терминала. Контролы используют меню/кнопки и числовые значения; мультивыбор содержит «Выбрать все / Снять все». У ПодбораПК свой видимый набор CPU, свои порции/число частей и лимитRAM; скрытая зависимость отCPU на другой странице устранена. Общие параметры PDF/цвета отображаются внизу и на странице PDF/цвет; команда содержит их значения полностью.

В консоли выполняются только проверенные команды uCode. Кнопка «В консоль» переносит текущие переключатели; «Показать кнопками» возвращает одну команду в форму. Несколько строк составляют последовательную очередь без скрытых осей; все строки разбираются до первого запуска. Есть план, журнал, отмена, сохранение TXT, запоминание последней очереди и документ [TEST_COMMANDS.md](TEST_COMMANDS.md) с простыми и сложными примерами.

По уточнению пользователя сохраняется **только локальная папка**, **только текстовые результаты**. Google Drive/VPS не подключаются. PDF и исходныеTXT сохраняются в исходных папках; в новом архиве их нет.

## Архитектура

- `test_navigation.HubNotebook`: один главный пункт Тесты и вложенный ttk.Notebook. Старые вызовы `app.notebook.select(app.pages['lab'])` поддерживаются и выбирают соответствующую вложенную страницу. Обработчики истории и кнопок получают реальное выбранное содержимое.
- `test_commands`: парсер shlex/argparse без shell, языкверсии1, конвертация в реальные LabConfig/PipelineConfig/SearchConfig/научную методику. Сериализация каждого пользовательского поля, preview и последовательное исполнение. Никаких eval/exec/subprocess произвольного текста. Историческая методика не принимает выключение QA или произвольную геометрию.
- `test_console_ui`: ввод/план/журнал, GUI↔команда и существующая owned worker/cancel очередь. Текущий текст сохраняется в .local-state/console-commands.txt. Предварительный план не запускает CPU-нагрузку или генерацию.
- `test_archive`: декоратор public run_lab/run_search/run_pipeline_lab/run_scientific/run_experiment/run_suite архивирует только после возврата измеряемой функции. GUI задаёт единый корень через ContextVar внутри своего рабочего потока; вложенные scientific этапы получают отдельные записи. CLI test использует тот же архив. Вызовы API без явного scope сохраняют _test_archive рядом с соответствующими результатами, чтобы тестовые fixtures и чужие выходные папки оставались изолированными.
- `archive_ui`: единая история всех типов с пагинацией, выбором локальной папки, браузерным индексом и импортом предыдущих результатов. Старый подробный просмотр lab сохранён отдельно как История.

## Формат архива и ограничения

По умолчанию GUI/новыйCLI: output/test-archive/. Выбранная папка хранится в .local-state/archive-settings.json. `catalog.sqlite` содержит только локальный индекс. Каждый runs/<uuid>/ содержит независимые report.json, report.html, ОТЧЁТ.txt. HTML самодостаточен и содержит таблицу результатов и полные текстовые параметры; в нём нет несуществующих ссылок на PDF. Варианты с ошибками/отменой/UNVERIFIED сохраняются с исходными статусами, без повторной QA и без повышения доPASS.

Идентичный исходный отчёт определяется по хешу исходного расположения и bytes; повторный импорт идемпотентен. Конкурирующие процессы используют SQLite BEGIN IMMEDIATE, уникальный ключ и атомарныйHTML-индекс. Результаты добавляются, прежние снимки не перезаписываются и не удаляются. Ошибка архивирования сохраняется в archive-status.json и показывается отдельно, не меняет научный статус или измеренные секунды. Неполные служебные файлы не удаляются автоматически.

Сохраняются данные моделиCPU/числа ядер/доступныхCPU, RAM, диска иОС из исходного отчёта, параметры, версии, все повторы, тайминги, наблюдения CPU/RSS, статусы и ошибки. `archive_environment` отдельно описывает ОС/Python/базовые пакеты машины, создавшей снимок; это не доказательство исходного runtime старого/чужого теста. Пароли/токены, абсолютные машинные пути, QR-матрицы/полезная нагрузка/12-значные коды отфильтровываются из текстового снимка. Исходный отчёт не переписывается. Исходный JSON до64МиБ; GUI показывает первые1000 записей страницами, браузерный индекс содержит все записи. Это не база измеренного сравнения разных ПК с общей методикой: разные версии/настройки/QA нельзя незаметно смешивать в один рейтинг.

Автоматические проверки — только малые PDF до7 страниц. 200/1000/10000/100000, тяжёлые очереди и визуальную приёмку выполняет пользователь. Компоновка проверяется программно при100/125/150% без ослабления прежнего предела1326×668.

## Общее хранилище позже: реальные варианты

Текущий пакет не создаёт аккаунты, сетевые службы, облачную папку и загрузки. Для одного владельца Windows/Mac проще выбрать локальную папку, которую синхронизирует Google Drive для компьютера. ПоддержкаLinux у официального desktop-клиента отсутствует. Запись файла в такую папку подтверждает только локальное сохранение, не завершение загрузки в облако. [Системные требования Google](https://support.google.com/drive/answer/2375082).

Для множества независимых пользователей личная общая папка Google Drive не делает их файлы автоматически собственностью владельца2ТБ: действует владение файлами/личные квоты; Shared drives с организационным владением относятся кGoogle Workspace. Нельзя обещать универсальный сбор на личные2ТБ без входа/прав и учёта этой модели. [Владение файлами](https://developers.google.com/workspace/drive/api/guides/about-files), [Shared drives и квоты](https://developers.google.com/workspace/drive/api/guides/about-shareddrives).

Для централизованного архива многих пользователей практичен HTTPS-приёмник наVPS с персональными ключами, ограничением размеров и неизменяемыми записями, либо организационный Shared drive с настроенными правами. Нужны выбранные сервер/домен/TLS, учётные данные и политика видимости; они не выдумываются и не вшиваются в публичный клиент. Живой SQLite-каталог не следует синхронизировать как общую многопользовательскую базу. Переносимый контракт — отдельные текстовые JSON/HTML записи; будущий сервер строит собственный индекс. Это следующий отдельный этап после выбора реального хранилища пользователем.
